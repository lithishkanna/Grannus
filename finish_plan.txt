## 0. Product rules

- Grannus **routes and translates. It does not diagnose.** Routing is by complaint category.
- Use "urgency" and "self-care information". Never claim "diagnosis", "validated", or "clinician-approved" until a real clinician has signed off.
- Show a **"Demo: synthetic data, not medical advice"** banner on every screen until a hospital pilot is approved.
- Out of scope for now: WhatsApp, IVR, ASHA mode, and real clinical validation. Without real validation, this is a prototype and must not be used for real care decisions.

### Urgency tiers

| Tier | Meaning | Patient sees |
|---|---|---|
| `emergency` | Red flags | Full-screen "Call 108", nearest emergency facility, ER alerted |
| `doctor_today` | Review within 24 h | Queued, with wait estimate |
| `doctor_soon` | Review in 2 to 3 days | Asynchronous doctor reply |
| `self_care` | Mild | Approved remedy, "See a doctor if...", check-in |

## 1. Who can see what (access matrix)

Enforce on the **server** with role, `hospital_id`, and ownership checks on every query, plus row-level security as a second layer. Hiding a button in the UI is not access control.

| Role | Can see | Cannot see |
|---|---|---|
| **Patient** (phone OTP) | Only profiles under their verified number (self and family): reports, doctor replies, history, check-ins | Other numbers' data; any doctor, nurse, or admin screen |
| **Emergency guest** (name only) | Only the one case they created | History, profile lists, any other case |
| **Doctor** | Cases assigned to them, their own replies, triage details, and patient details attached to those cases. Unclaimed cases in their department show only complaint, tier, age, gender. | Other doctors' cases, the full phone number, the whole account |
| **Nurse** | Queue metadata for their hospital | Reply content they did not write |
| **Admin** | Users, roster, routing logs, deletion log | Clinical content |

## Block H1: Authentication (P0)

### H1.1 Remove the open login
- [ ] In `auth.py`, delete the legacy branch of `authenticate_credentials` that returns `True` for unknown users with no password.
- [ ] In `main.py` `/auth/login`, remove the "user_id plus role" path. Only existing staff accounts with a correct email and password can log in.
- [ ] Staff accounts are created by an admin. Doctors have a registration number verified by the admin, not by a regex.

### H1.2 Real phone OTP (patients)
- [ ] **Delete `dev_otp_hint` from the API response completely.** OTPs never appear in any response, log, or error.
- [ ] Add an `SmsProvider` interface with implementations for Twilio Verify (default) and MSG91. Check current India SMS and DLT requirements with the provider.
- [ ] Flow: enter phone, SMS arrives, enter the code, tap **Verify**, then the dashboard.
- [ ] Codes: 6 digits, 5-minute expiry, single use. If the provider doesn't verify for you, store a per-OTP random salted hash (not a fixed salt).
- [ ] Limits: 5 attempts per code, 30-second resend cooldown, per-number and per-IP rate limits, and a daily SMS cap to prevent SMS-pumping abuse.
- [ ] Development uses the provider's test numbers. No fixed code in the repository.
- [ ] OTP state lives in the database or the provider, never in process memory.

### H1.3 Emergency access without OTP
- [ ] An **Emergency** button on the login screen asks only for a name (age optional).
- [ ] The **"Call 108" screen appears instantly on the device before any API call**, so a server failure cannot delay it.
- [ ] The backend creates a guest emergency case with a random, unguessable case token held on that device, and alerts the hospital ER.
- [ ] The guest token can read **only that one case**. It cannot list or open anything else.
- [ ] The case is marked "unverified" so duty staff can confirm. Add generous IP and device rate limits to prevent ER flooding.
- [ ] A guest can later verify their phone by OTP and attach the case to their account.

### H1.4 Sessions
- [ ] Short-lived access tokens, refresh tokens, logout, and revocation.
- [ ] The token carries `user_id`, `role`, `hospital_id`, and (for patients) `account_id`.
- [ ] Remove any fallback signing secret.

**Acceptance tests (`tests/test_h1_auth.py`)**
- `POST /auth/login {"user_id":"x","role":"admin"}` returns 401.
- An OTP request response contains no code field, and no log line contains a code.
- A wrong code 5 times locks the attempt, and a used or expired code fails.
- A guest token reads its own case and gets 403 on any other case or list.
- Starting with `ENV=production` and no SMS provider configured fails at startup.

## Block H3: Authorization everywhere (P0)

Apply the access matrix to **every** route. Write one shared dependency (`require_role`, `require_profile_access`, `require_case_access`) and use it on all endpoints.

- [ ] **H3.1** Patient endpoints: load profiles and consultations filtered by the token's `account_id`. Accessing another account's profile returns 403 (or 404).
- [ ] **H3.2** Doctor endpoints: only cases assigned to that doctor (or unclaimed in their department, with limited fields). Claiming is atomic.
- [ ] **H3.3** Mask data by role: doctors get age and gender, not the full phone number. Nurses and admins never receive clinical text.
- [ ] **H3.4** Protect `/escalate`, `/thread` (GET and patient reply), `/check-in`, `/pipeline/job-status/{id}`, and `/media/stream`.
- [ ] **H3.5** `/pipeline/submit-audio` and `/pipeline/process-audio` must check the token **before** reading or validating the upload.
- [ ] **H3.6** Optional per-profile 4-digit PIN for sensitive profiles. Warn users that anyone with the phone and SMS access sees all profiles under the number.
- [ ] **H3.7** "This isn't my number" action and a recovery path for recycled numbers.
- [ ] **H3.8** Every read and write of clinical data writes an audit row.

**Acceptance tests (`tests/test_h3_access.py`)**
- Patient A gets 403 or 404 on patient B's profile, consultation, thread, and audio.
- Doctor X gets 403 on doctor Y's assigned case.
- A patient token gets 403 on every doctor and admin route.
- Every route is covered by a parametrized test that calls it with no token (401), the wrong role (403), and the right role (success).

## Block H4: Audio retention (24 hours) (P1)

**Keep permanently** (subject to your retention and erasure policy): original and English transcripts, extraction, urgency tier, doctor reply text, back-translation.
**Delete after 24 hours:** patient recordings and doctor recordings in storage, temp files, and caches.

- [ ] **H4.1** Every audio file has `created_at` and `delete_after` (default `created_at + 24h`) stored in the database.
- [ ] **H4.2** A **database-driven** deletion job runs every 5 to 10 minutes. It must survive restarts. No in-memory timers.
- [ ] **H4.3** The job deletes the object from storage, clears any cached copies, and writes a row to `deletion_log`.
- [ ] **H4.4** The doctor's voice reply is replayable after 24 hours by regenerating audio from the stored text, so only text needs to be kept.
- [ ] **H4.5** Do not keep recordings in local temp directories beyond the pipeline run. Delete them in a `finally` block.
- [ ] **H4.6** If a transcript is missing or low confidence when the audio expires, mark the case "needs re-record" and notify the patient.
- [ ] **H4.7** Signed audio URLs expire in minutes, and return 404 once the file is gone.
- [ ] **H4.8** Show a visible note in the UI: "Recordings are deleted after 24 hours. Text is kept."

**Acceptance tests (`tests/test_h4_retention.py`)**
- Advance the clock 25 hours: no audio object remains, and all text is still present.
- The deletion job survives a restart and still deletes overdue files.
- A deleted audio URL returns 404.
